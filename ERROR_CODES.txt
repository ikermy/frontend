--------------------------------------------------------------------------------
КАК ФРОНТ ФОРМИРУЕТ ОШИБКУ (app/shared/api/client.ts)
--------------------------------------------------------------------------------
При ответе !response.ok фронт достаёт из JSON-тела BFF поля { code, message }.
Итоговый объект ApiError = { message, code, field?, details? }, где:

  code    = body.code                — если BFF вернул свой код
          = `HTTP_${status}`         — если код не пришёл (например 502, 404)
          = "REQUEST_ERROR"          — сетевая ошибка / тело не JSON
  message = body.message              — если есть
          = response.statusText       — иначе
          = "API request failed"      — при сетевом сбое

================================================================================
1. БИЗНЕС-КОДЫ BFF (основные, приходят в body.code)
================================================================================
Код                        HTTP   Показывать пользователю
-------------------------  -----  ---------------------------------------------
VALIDATION_ERROR           400    Ошибка входных данных (можно взять message/details)
MISSING_DEPENDENCY         400    Не хватает обязательного поля
INSUFFICIENT_FUNDS         402    Недостаточно средств (details.topUpRequired)
PARTIAL_FUNDS              200    НЕ ошибка — частичный успех
DUPLICATE_REQUEST          200    НЕ ошибка — повтор идемпотентного запроса
BARCODEGEN_ERROR           503    Сервис генерации недоступен (сюда же обёрнуты
                                  ошибки Auth-профиля — см. §4)
BILLING_ERROR              503    Биллинг недоступен
INTERNAL_ERROR             500    Внутренняя ошибка сервера
UNAUTHORIZED               401    Не авторизован
LOGIN_FAILED               500    Ошибка входа
REGISTRATION_FAILED        500    Ошибка регистрации
EMAIL_EXISTS               409    Email уже зарегистрирован
REQUEST_IN_FLIGHT          409    Дублирующий запрос уже обрабатывается

--- Верификация email (auth RPC: requestEmailVerification / verifyEmail) ---
На текущий момент BFF может отдавать эти ошибки как BARCODEGEN_ERROR с
message из §4. Коды ниже — целевой маппинг BFF при проксировании auth.
EMAIL_VERIFICATION_FAILED      400    Неверный/истёкший токен подтверждения email
EMAIL_ALREADY_VERIFIED         409    Email уже подтверждён
EMAIL_NOT_LINKED               400    Нет привязанного реального email для подтверждения
EMAIL_VERIFICATION_SEND_FAILED 503    Не удалось отправить письмо подтверждения
                                      (нет SMTP/транспорта)

================================================================================
2. HTTP-КОДЫ-ЗАГЛУШКИ (когда body.code отсутствует)
================================================================================
Формат: HTTP_<status>. Наиболее вероятные:
  HTTP_400  — некорректный запрос
  HTTP_401  — не авторизован (например login/telegram)
  HTTP_403  — доступ запрещён
  HTTP_404  — не найдено
  HTTP_409  — конфликт
  HTTP_422  — необрабатываемые данные
  HTTP_500  — ошибка сервера
  HTTP_502  — неверный шлюз (прокси до бэкенда недоступен)
  HTTP_503  — сервис недоступен
  HTTP_504  — таймаут шлюза

================================================================================
3. СЕТЕВЫЕ / КЛИЕНТСКИЕ КОДЫ
================================================================================
REQUEST_ERROR   — сетевой сбой, CORS, не-JSON тело. message = "API request failed"
                  или текст ошибки fetch. Обычно показывать generic-уведомление
                  «Не удалось связаться с сервером, попробуйте позже».

6. РЕКОМЕНДАЦИИ ДЛЯ UI УВЕДОМЛЕНИЙ
================================================================================
- Сначала проверять body.code (UNAUTHORIZED, EMAIL_EXISTS, INSUFFICIENT_FUNDS,
  REQUEST_IN_FLIGHT, VALIDATION_ERROR, *_ERROR из §1), затем fallback HTTP_<status>,
  затем REQUEST_ERROR.
- INSUFFICIENT_FUNDS: читать details.topUpRequired -> показать CTA «Пополнить».
- PARTIAL_FUNDS и DUPLICATE_REQUEST — не уведомлять об ошибке (успех/кэш).
- REQUEST_IN_FLIGHT — показать «Запрос уже обрабатывается».
- BARCODEGEN_ERROR/BILLING_ERROR — ошибка внешнего сервиса, показывать generic +
  предложить повторить позже.
- Верификация email: success → показать подтверждение и обновить профиль
  (isEmailVerified=true); EMAIL_ALREADY_VERIFIED — не ошибка, показать
  «уже подтверждён»; EMAIL_VERIFICATION_FAILED/EMAIL_NOT_LINKED — показать
  сообщение и предложить привязать/запросить письмо повторно.
- Для специфичных сообщений (Telegram, email) матчить message (см. §4/§5).
